# 静态模块表（配置文件）说明与示例

本目录是 `IpcConfigLoad()` / `IpcModuleOptions.confPath` 读的那个文件的说明与样例。  
默认路径是 `IPC_CONF_DEFAULT`，即 `/etc/ipc-modules.conf`。

---

## 1. 配置文件定义了什么

一句话：**「谁（命名空间 + 模块标识）在哪个地址上服务、由哪个 UID 注册」**。

| 字段         | 类型     | 约束                             | 作用                    |
| ---------- | ------ | ------------------------------ | --------------------- |
| `ns`       | 命名空间   | 1–15 字节；只允许字母、数字、`_`、`-`       | 在同一台机器上隔离多套部署         |
| `moduleId` | 模块标识   | *1–31 字节；只允许字母、数字、`_`、`-`、`.`* | 模块的名字，业务层用它寻址         |
| `uid`      | 授权 UID | 十进制数字，无符号位，0 – 4294967294      | **唯一**允许注册/服务该模块的 UID |
| `path`     | 端点路径   | 绝对路径，1–107 字节，不能是 `/`          | 该模块 socket 文件的固定位置    |

配置**不**包含的东西（有意为之，别在这里找）：

- **不做调用授权**（谁能给谁发消息）。设计前提是「同一命名空间内所有模块互通」；  
  真要限制「A 只能调 B」，那是另一套调用 ACL，不能和这里的 UID 身份校验混在一起。
- **不含回调、事件号、超时、缓冲区大小**。那些是代码里的事，不是部署策略。
- **不含 socket 的属组与权限模式**。当前由 `IpcModuleOptions.groupName` 传，  
  模式固定。这一条**建议改**，见第 7 节待定项。

---

## 2. 格式规则

```text
# 注释行
<ns>  <moduleId>  <uid>  <path>
```

- **每行恰好 4 个字段**，字段之间用任意长度的空白分隔（空格和 TAB 都可以）。
- **`#` 到行尾是注释**，可以在行首，也可以在行内（行内注释是支持的）。  
  ⚠️ 正因为如此，**socket 路径里不能出现 `#`**，否则会被当成注释截断。
- 空行、纯注释行忽略。
- **大小写敏感**，逐字节比较。`Logger` 和 `logger` 是两个不同的模块。
- 建议显式指定完整路径，不要在配置里用变量（解析器不做任何展开）。
- 行尾的 `\r` 会被剥掉，所以用 Windows 编辑器存成 CRLF 也不会出错  
  （老实现没做这一步，会把 `\r` 当成路径的一部分，新实现要修掉）。

### 整表拒绝的规则

只要有一行不合格，**整个文件都被拒绝**，返回 `IPC_ERR_CONFIG`，不会「跳过坏行用剩下的」。  
具体触发条件：

| 情况                  | 例子                        |
| ------------------- | ------------------------- |
| 字段数不是 4             | `demo Sender 1001`        |
| 命名空间/模块标识为空或超长      | 见 `invalid/06`            |
| 命名空间/模块标识含非法字符      | 见 `invalid/07`            |
| uid 不是纯十进制数字        | `-1`、`+1001`、`1e3`、`root` |
| 路径不是绝对路径            | `./Sender.sock`           |
| 路径是 `/` 或超长         | `/`                       |
| `(ns, moduleId)` 重复 | 见 `invalid/02`            |
| `path` 重复（跨命名空间也算）  | 见 `invalid/03`            |

> 为什么路径重复也拒绝：socket 文件路径是**全机唯一**的，两个模块共用一个路径，  
> 后注册的会把先注册的那个顶掉。这类配置错误在运行时表现为「莫名其妙收不到消息」，  
> 很难查，所以在加载期就拦掉。

## 4. 光有配置文件不够：配套的目录与权限

配置文件只声明策略，**强制执行靠文件系统权限**。库内的 UID 自检只是防误用，  
不是安全边界。必须由受信任的启动流程预先准备好目录：

```bash
# 通信组（所有服务身份都是它的成员）
groupadd ipc-members

# 命名空间根目录：root 所有 + 组可进入、不可写
install -d -o root -g ipc-members -m 0750 /run/example-ipc

# 每个服务一个子目录，属主是该服务 UID，组是通信组
install -d -o 1001 -g ipc-members -m 0750 /run/example-ipc/A
install -d -o 1002 -g ipc-members -m 0750 /run/example-ipc/B
install -d -o 1003 -g ipc-members -m 0750 /run/example-ipc/C

# 配置文件本身：root 所有，服务只读
install -o root -g root -m 0644 /path/to/03-three-uid-nine-modules.conf /etc/ipc-modules.conf
```

对应关系（与 `conf/03-three-uid-nine-modules.conf` 一致）：

| 对象                | 属主:属组                 | 模式     | 这个权限挡什么                       |
| ----------------- | --------------------- | ------ | ----------------------------- |
| 命名空间根目录           | `root:ipc-members`    | `0750` | 非组成员连路径都进不去                   |
| 服务子目录             | `<该 UID>:ipc-members` | `0750` | 别的服务**不能在别人的目录里建/删/换** socket |
| 模块 socket（库注册时创建） | `<该 UID>:ipc-members` | `0620` | 组内可写 → 跨 UID 能发数据报；组外什么都不能    |
| 配置文件              | `root:root`           | `0644` | 服务改不了策略（但见下面第 7 节第 3 条）       |

⚠️ **socket 的权限不是靠 umask 蒙对的。** `bind()` 建出来的文件会带上进程 umask，  
所以实现必须是：`umask(0077)` 包住 `bind()`，随后**对路径**（不是 fd）显式  
`chmod`/`chown` 到目标值，再 `lstat` 回读校验一遍。已确认 `fchmod`/`fchown` 对  
已 bind 的 unix socket fd 是**静默 no-op**，走 fd 改权限会以为改了其实没改。

## 5. 谁读它、什么时候读

- 由 `IpcRegister()` 在注册时读一次，**进程生命周期内复用**，不会每次发送都去读文件。
- 每个进程可以注册多个模块（多次 `IpcRegister`），各自独立。
- 一个 C 文件也可以完全不用这个文件：`IpcConfigParse()` 直接吃内存字符串，  
  单元测试和工具走这条路，不依赖磁盘。

## 6. 常见坑

1. **uid 写名字不写数字**：只接受十进制数字。写 `logger` 会整表被拒。  
   用名字还得查 passwd、受 NSS 配置影响，且配错时更难发现。
2. **同一模块名出现在多个命名空间，而注册时没指定 ns**：库报 `IPC_ERR_CONFIG`  
   （歧义）。见 `conf/02-two-namespaces.conf` —— 这种情况必须显式给 `ns`。  
   `conf/04-testlab.conf` 里的 `extra A1` 就是专门用来测这条的。
3. **路径重复**：包括跨命名空间。两个命名空间用同一个 socket 路径是被拒的。
4. **行内出现 `#`**：路径里带 `#` 会被截断。别用带 `#` 的目录名。
5. **Windows 编辑后变 CRLF**：当前设计会剥掉行尾 `\r`，但**别依赖它** ——  
   这个仓库自己的纪律就是所有文本文件钉 `eol=lf`（见 `.gitattributes`）。

## 7. 待定项（设计还没锁，需要拍板）

1. **socket 的属组要不要进配置文件？**  
   现在 `groupName` 是 `IpcModuleOptions` 的字段，也就是说「谁能访问这个 socket」  
   这条策略一半在配置、一半在代码里。handoff §5.2 的权限表是把它当部署策略的。  
   建议加一个**可选第 5 字段**：`<ns> <moduleId> <uid> <path> [group]`，  
   用 `-` 表示「沿用进程默认」。不写第 5 字段时行为不变，所以是向后兼容的补充。
2. **条目数上限。** 现在解析器是动态扩容、没有上限，一个 1 MiB 的文件  
   （`IpcConfigLoad` 的读取上限）能塞进几万条。建议加  
   `IPC_CONFIG_MAX_ENTRIES`（比如 4096），超了直接 `IPC_ERR_CONFIG`。
3. **库要不要强制校验配置文件自身的属主与模式？**  
   上一版在这件事上踩过坑：README 声称「注册时拒绝 group/other 可写的配置文件」，  
   但实现检查的是 **socket 目录**、不是配置文件，验证用例验的也是文件系统性质 ——  
   文档承诺和实现不一致。  
   本版的立场是**不检查**（否则没有 root 的开发环境根本跑不起来），  
   所以「`root:root 0644`」是**部署纪律**、不是库的保证。  
   要不要加一个可选严格模式（例如 `IpcModuleOptions.strictConfPerm`），需要拍板。
